## 3. ข้อบกพร่องที่พบและแก้ระหว่างงานนี้

### 3.1 pattern ต้องห้ามใน R3.4 กว้างเกินจริง (แก้ `normalize.py`)

requirements เขียนช่วงเป็น `[\u0e00-\u0e7f]\s+[\u0e30-\u0e4e]` แต่ช่วง U+0E30-U+0E4E
รวมสระที่กินที่ซึ่งตามหลังช่องว่างได้อย่างถูกต้อง: ะ า ำ เ แ โ ใ ไ ๅ ๆ

วัดผลด้วยช่วงตามตัวอักษร: "ละเมิด" 197 จาก 608 หน้า และทุกรายการเป็นข้อความไทยที่ถูกต้อง
เช่น `คงอยู่ และเปลี่ยนชื่อ`, `อัฉริยะ และข้อมูลูขน`, `รายวิชา เทคโนโลยี`, `ตัดออก เปลี่ยนแปลง`

ถ้าปฏิบัติตามตัวอักษรจะลบช่องว่างเหล่านั้นและทำให้คำติดกันผิด จึงจำกัดขอบเขตไว้ที่
combining mark จริง (`\u0e31\u0e34-\u0e3a\u0e47-\u0e4e`) ซึ่งเป็นเจตนาของ R3.3/R3.4
`_MARKER_SPACE_RE` ที่ใช้ลบช่องว่างก็ถูกแก้ตามด้วย มิฉะนั้นจะทำข้อความเสียหายจริง

### 3.2 PUA U+F70C ยังไม่มี mapping (เพิ่มใน `THAI_PUA_TO_MARK`)

พบ 14 ครั้งใน BIT2565, DSBA2565, IT2560 ยืนยันเป็นไม้ไต่คู้ U+0E47 จากสี่คำที่ไม่เกี่ยวกัน:
`เว\uf70cบ` → เว็บ, `อ\uf70cอบเจกต์` → อ็อบเจกต์, `พล\uf70cอต` → พล็อต, `แจ\uf70cกซ์` → แจ็กซ์
(เป็น glyph variant คนละตัวของ mark เดียวกันกับ U+F712 ตามความสูงของ base)

หลังเพิ่ม mapping: PUA ที่ไม่รู้จักในคลังเหลือ 0 รวม mapping ทั้งหมด 13 รายการ

### 3.3 `span["size"]` เชื่อไม่ได้ (แก้ `effective_font_size`)

`PH_D_IT2561_old.pdf` หน้า 9, 10, 14 มี span รายงาน `size = 2.1 pt` ขณะที่ bbox ของ glyph
สูง 19.3 pt ทำให้ baseline tolerance เหลือ 0.41 pt และวรรณยุกต์ 5 ตัวหา base ไม่ได้
ทั้งที่อยู่ติดกับ base ในสตรีม แก้โดยใช้ `max(font_size, bbox.height)` เป็นตัวคูณ tolerance
ผลคือหน้าที่ mark หา base ไม่ได้ลดจาก 3 หน้าเหลือ 0 หน้า และไม่กระทบ glyph ปกติ

### 3.4 เลข `order` ของบรรทัดไม่ต่อเนื่อง (แก้ `line_assembler.py`)

property test จับได้ว่าบรรทัดที่มีแต่ whitespace ถูกทิ้งหลังจากได้เลข order ไปแล้ว
ทำให้ลำดับเป็น `[1]` แทน `[0]` แก้โดยกำหนดเลขหลังกรองบรรทัดว่างเสร็จ

## 4. ข้อเท็จจริงเชิงเทคนิคที่ยืนยันแล้ว (ใช้กำหนดสัญญาของชั้นถัดไป)

* bbox ระดับ glyph **มีความกว้างเป็นศูนย์ได้** ดังนั้น `BBox.is_valid()` (บังคับ x1 > x0
  ตาม R9.2) ใช้ได้กับ bbox ระดับบรรทัด/provenance เท่านั้น ห้ามใช้ตรวจ glyph
* glyph ความกว้างศูนย์ **ไม่ใช่ combining mark ทุกตัว** — พบ `^` (U+005E) และ `_` (U+005F)
  ความกว้าง 0 ในฟอนต์ของคลังนี้ การตัดสินว่าเป็น mark จึงต้องดูทั้ง mark class และความกว้าง
* combining mark ทุกตัวที่สุ่มตรวจมีความกว้าง 0.00 pt พอดี (ไม่ใช่ค่าน้อย ๆ)
* Line_Assembler ต้องเรียงเป็น **cluster** ไม่ใช่เรียง glyph ตาม X แบบแบน เพราะ mark
  มี x0 น้อยกว่า base ได้ ถ้าเรียงแบบแบนจะทำลายลำดับที่เพิ่งจัดไว้

## 5. หมายเหตุความต่างจากตัวเลขที่บันทึกไว้ก่อนหน้า

* หน้าข้อความน้อยกว่า 120 อักขระ: วัดรอบนี้ได้ **974** หน้า ตัวเลข 979 ที่บันทึกไว้ก่อนหน้า
  มาจากการนับด้วยเกณฑ์คนละชุด (ก่อนมี `Text_Extractor`) ให้ใช้ 974 เป็นค่าอ้างอิงต่อไป
* `pages_zero_char = 0` แม้จะมีหน้าสแกน 745 หน้า เพราะหน้าสแกนยังมี header/เลขหน้าเป็น
  text layer อยู่ ดังนั้น **ห้ามใช้ `char_count = 0` เป็นเงื่อนไขเดียวในการส่ง OCR**
  ต้องพึ่ง `image_area_ratio` ตาม R4.7 ด้วย (ตัวอย่าง AIT2566 หน้า 120: 89 อักขระ,
  image_area_ratio = 0.918)
